The unchanged Qdrant/Neo4j closures are important: the shared infrastructure still performs real graph/vector operations, so moving re-export paths alone does **not** isolate their rebuilds. `cargo build -p graph_neo4j` is not proof that a linked Worker binary stops rebuilding. This needs controlled compile-unit and linker timings in CI.

Concrete ownership improvements in the candidate:

- **Temporal:** `infrastructure` no longer depends on `temporalio-sdk`, `temporalio-sdk-core`, `temporalio-client`, `temporalio-common` or `temporalio-macros`. The new `temporal_gateway` owns actual client connection, typed resume/LLM signals and running-workflow readback. `temporal_worker` imports Workflow/Activity SDK types directly. The Outbox Worker no longer receives the Temporal SDK transitively via infrastructure. Default `integration_harness` dependencies do not force this gateway; its real Temporal integration is enabled by `e2e`.
- **Analytics protobuf:** `infrastructure/build.rs` and the general `tonic_adapter` were removed. The only active analytics health client is now owned and protobuf-generated by `cli_tools`; `analytics_svc` retains its separate server code generation. The Worker release image still includes `cli_tools`, so analytics proto remains part of the *full image context*, but it no longer invalidates every consumer of `infrastructure`.
- **Graph/vector:** Neo4j and Qdrant SDK imports use their existing dedicated crates directly, without old general-infrastructure SDK re-export modules. PostgreSQL remains authoritative; projections are derived from PostgreSQL/Outbox.

The graph count covers all selected compile owners and optional edges, not inferred isolated runtime processes. `cargo metadata --locked --offline --no-deps` passes for the candidate. Local offline `cargo check -p seo_application` and `cargo test -p seo_application --lib` passed (67/67); the `truth_domain` and `seo_domain` library tests passed too. Some Worker and E2E dependencies are unavailable in the local offline cache, so complete `cargo tree -e features`, Worker rebuild/link timings and real PostgreSQL/Temporal E2E require the CI runner. No complete-build-duration claim is made here.

## Architecture decision and acceptance

**Candidate A — modular monolith:** GO for typed module/owner boundaries. It preserves one transaction owner, one Outbox delivery owner, one Temporal orchestration runtime, no new RPC transport and one `ci.yml`. Individual SEO/Truth step composition is an application decision; it must not be fixed by storage technology or a hard-coded external-service sequence.

**Candidate B — separate Temporal Activity processes:** NO-GO at this stage. No measured linker or E2E improvement justifies extra binaries, task queues, deployment topology or failure modes. Independently compiled crates are not independent runtime services.

New deployments and existing databases require the same verified precondition; a green source grep alone does not install constraints in production. If the installer rejects duplicates or wrong constraint definitions, leave writers stopped and open a reviewed data-repair incident; **never** bypass verification or ACK ambiguous projections.

The existing `automation/run_graph_contract_gate.sh` is a **local smoke gate**, not a production migration tool. The existing `integration_harness::Neo4jHarness` must explicitly install and verify on a *real* disposable Neo4j instance before any projection test writes. A real concurrent-replay E2E must run via the **existing** `graph_query` selector (`--lib graph_capability_`) in the one `ci.yml` architecture owner, and the offline contract/mutation checks guard against accidentally removing schema installation, production verification or that E2E selector. No extra crate, process, job or workflow is justified by the repair. Verification of this owner invariant does **not** prove independent Cargo rebuilds, a ≤180-second green gate, causal graph revision semantics or freely composable business operations: those remain separate open acceptance blockers.

## Generic operation freshness before effectful composition

The legacy SEO recipe has a concrete `RawKnowledgeIngestion` -> stale
`VerifiedSupport` rule, but a fixed site-phase list cannot be the abstraction
for future business operations. `operation_protocol` therefore needs a
**versioned, owner-declared invalidation contract** on the artifact *type*; it
must not refer to 22 old phases, a remembered 56 steps, or the 73 Temporal
`#[activity]` wrappers as if those were a complete functional inventory.

The v2 generic contract adds `OperationContract.invalidates`, covered by the
owner fingerprint pinned in the immutable plan. The DAG validator must reject:

- reading an external or older produced artifact after an operation invalidates
  its schema type, unless a causally ordered producer explicitly refreshes it;
- placing an invalidator and reader on independent branches with no ordering
  edge, even if a deterministic topological sort happens to put them in a
  convenient order;
- independent operations which both invalidate the same artifact type: the
  planner cannot silently invent the order of competing state mutations.

For each produced artifact the validator conservatively inherits the artifact
types of **all its inputs**. Thus a `Draft` derived from old `VerifiedSupport`
still depends on that support after its direct schema changed to `Draft`:
invalidating `VerifiedSupport` also makes this previously derived `Draft` stale
for later consumers until its lineage is rebuilt in a causally ordered path.
This propagation is deliberately generic and contains no site-specific phase
names in the protocol implementation itself.

Independent business operations that have no causal conflict remain freely
reorderable. The existing five real pure semantic owners declare no invalidated
artifact types, and PostgreSQL's outbox lease reconciliation declares none:
neither is allowed to claim it refreshed authoritative Verified Truth.

**Important limit:** this is *in-plan* causal validation only. A nonempty
external `provenance` string is NOT verification that Truth is current. A future
effectful production Temporal runner must independently authorize effects and
admit external artifacts **and their inherited lineage** against authoritative
PostgreSQL revisions before
running a single Activity. No V1/V2 replay history is changed by this protocol
cut; no publication or Qdrant write is enabled by it. Only after real replay,
DB admission and durable effect-fence E2E may one effectful owner be opted in.

## 25 November 2026 — V3 Docker contexts and secret boundary, opt-in only

The preview `infra/temporal/Dockerfile.v3` separates two already existing
native executables into different final images: provider-free
`temporal_orchestrator` and PostgreSQL-only `temporal_pg_effects`. Unlike the
legacy `temporal_worker` image, the V3 evaluation path now accepts a separate
**Cargo metadata-derived, exact-commit build context per owner**:

| Optional Compose service | Explicit context variable | Cargo package / Docker target | Credential boundary |
| --- | --- | --- | --- |
| `temporal-orchestrator-v3` | `V3_PURE_BUILD_CONTEXT` | `temporal_orchestrator` / `pure` | No PG, Neo4j, Qdrant or Outbox DSN |
| `temporal-effect-dag-v4` | `V3_PURE_BUILD_CONTEXT` (same pure owner image) | `temporal_orchestrator` / `pure` | Separate `alegria-effect-dag-v4` queue; no provider credentials |
| `temporal-pg-effects-v3` | `V3_PG_BUILD_CONTEXT` | `temporal_pg_effects` / `pg` | Only restricted PostgreSQL secret file |
| Default `temporal-worker` | Unchanged repository context | Legacy provider-linked runtime | Existing PG + graph + vector owners remain linked |

The current checked-in-manifest conservative production graph (including
optional/build and target-specific workspace edges, excluding dev-only edges)
has these exact *manifest-derived* transitive workspace closures:

| Root | Workspace packages | Graph/Vector/PG owner sources |
| --- | ---: | --- |
| V3 pure `temporal_orchestrator` | 11 | none |
| V3 `temporal_pg_effects` | 10 | `postgres_store` only |
| Legacy `temporal_worker` | 24 | `postgres_store`, `graph_neo4j`, `vector_qdrant` |

These numbers are not resolved third-party dependency weights, compiler units,

uses actual locked Cargo metadata on a clean accepted source commit.

`automation/prepare_worker_build_context.py --image-owner
temporal-orchestrator-v3|temporal-pg-effects-v3` exports the selected owner’s
transitive workspace sources plus every necessary Cargo manifest and lockfile;
other workspace crates carry inert placeholders. The Dockerfile first copies

selected binary. Thus the former `COPY app`-from-whole-repository invalidation
is removed **only when the corresponding V3 context variable points to this
prepared owner-scoped export**. Compose retains `.` as a default context
fallback, but an ordinary root checkout has no generated `dependency-skeleton`
and is not a valid optimized V3 image input. The default path does not prove
independent rebuilds.

The pure V3 and PostgreSQL V3 services remain under the explicitly requested
`v3-evaluation` profile. The admitted V4 effect-DAG parent is in a **separate**
`v4-effect-evaluation` profile, reusing the provider-free image with a
different Task Queue (`alegria-effect-dag-v4`) and a distinct
`ALLOW_EFFECT_DAG_ORCHESTRATOR_V4` mode gate defaulting to `false`; its
`ALLOW_PURE_DAG_ORCHESTRATOR` is pinned to `false`. The V3 pure service still
polls `alegria-pure-dag-v3` with its original pure-only gate. These services
neither replace the default Worker nor automatically acquire
legacy Temporal history, task routing, projection/Outbox ownership, or
production authority. The PostgreSQL service receives no DSN environment

UID/GID/mode; **live verification on the chosen backend is mandatory**, and a
backend that does not meet the strict file contract must fail closed.

`infra/temporal/check_v3_evaluation_topology.py` statically and negatively
tests both V3/V4 profile gates, distinct parent queues and exclusive modes,
owner target selection, separate source context variables,
absence of forbidden direct provider dependencies, external-secret file path
and restrictive mode. The context generator has its own source-closure tests.
These are valuable regression contracts, **not measured Docker builds**:
no local Docker daemon ran cold/warm images, measured layer-cache invalidation,
verified secret mount mode, startup CPU/RAM or Task Queue ownership. No
deployment was cut over, no history drained/replayed, and no rollback was
tested. The V3 topology therefore remains a **NO-GO production experiment**;
the four PostgreSQL/Neo4j/Qdrant/Temporal owner rebuild measurement, signed
exact-source release and ≤180-second full CI target remain open.
